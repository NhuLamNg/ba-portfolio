Case study · Personal finance web app

Money Tracker

A web app that lets one person record income and spending across cash, bank accounts, e-wallets and credit cards, see where the money goes, and stay inside a budget. I ran the analysis as a Business Analyst would on a client project, then built and deployed it myself.

01 · The problem

Tracking money by hand was slow, scattered and easy to give up on

Before the app, the user kept notes on the phone, then copied them into Excel files split by month. On busy days nothing got recorded at all. The elicitation session confirmed three main pains.

Recording takes too many steps

Remember the spend, open the right file, find the right sheet, type it in.

1–2 min per entry, often skipped

No single view of all wallets

Bank app, e-wallet, cash in hand: each checked separately and added up manually.

3–5 min and 3–5 apps per check

No idea where the money goes

Free-text categories (“cf”, “ăn”, “food”) made monthly totals unreliable, so overspending showed up only at month end.

30–60 min a month to build a report

Target outcome: record a transaction in 15 seconds or less, always know the total across every wallet, and see the spending breakdown instantly.

Example: UC-05 Record an expense

Main flow, as specified and then built:

  1. User taps the floating “+” button, available on every screen.
  2. Form opens on “Expense” by default.
  3. User enters an amount (required, whole VND, greater than 0).
  4. User picks an expense category; income categories are hidden.
  5. User picks an active wallet; archived wallets are hidden.
  6. Date defaults to today; future dates are blocked.
  7. Optional payee and note, up to 100 characters.
  8. System saves and lowers the wallet balance in the same step, then refreshes the dashboard.

User stories

US-01

As a user, I want to record an expense in a few taps, so that I record it on the spot instead of forgetting it.

  • Given I have an active wallet, when I save 65,000 ₫ under “Ăn uống”, then the entry appears and that wallet's balance drops by 65,000 ₫.
  • Given the amount is 0 or empty, when I save, then I see “Amount must be greater than 0” and nothing is saved.
  • Given I pick a future date, when I save, then it is blocked.
US-02

As a user, I want one total across all my wallets, so that I know what I have without opening several apps.

  • Given several active wallets, when I open the dashboard, then the total equals the sum of their balances.
  • Given an archived wallet, then it is excluded from the total.
  • Given I switch month, then the total does not change; only monthly income and spending do.
US-03

As a user, I want to move money between my wallets, so that every balance stays correct.

  • Given source and target are the same wallet, then the transfer is rejected.
  • When a transfer is saved, then both balances change together, or neither does.
  • Then the transfer is not counted as income or spending in reports.
US-04

As a user, I want a monthly limit per category with an early warning, so that I can slow down before I overspend.

  • Given I set a threshold, then it must be between 50% and 99%, and a warning at 100% always applies.
  • When spending passes the threshold, then I am warned, but I can still record expenses.
  • Given I edit a past entry, then that month's budget progress updates.

08 · Phase 5

AI assistant: specifying behaviour, not just a chat box

The interesting work was defining what the assistant must do when the input is incomplete, ambiguous or repeated.

Happy path

  1. User types “Nhận lương 20 triệu vào VCB”.
  2. The server sends the message to the model along with that user's own wallets and categories.
  3. The model extracts type, amount, category and wallet, and calls the createTransaction tool.
  4. The server saves through the same database function as the manual form, so every rule still applies.
  5. The assistant confirms, and balances on screen refresh.

Edge cases I specified

  • Missing information. If the wallet or type is unclear, the assistant asks a follow-up question instead of guessing.
  • Future intent. “Mai chắc mua giày 2 triệu” is a plan, not a spend, so nothing is recorded.
  • Double submit. Each request carries an ID stored in idempotency_keys, so a network retry never creates a duplicate entry.
  • Cost control. A per-user hourly limit in ai_chat_rate_limit caps model usage.
  • Audit. Each entry is tagged manual or ai_assistant.

09 · Decisions and trade-offs

Choices I made, and why

Changed the build stack after the specs

The specs assumed React with a FastAPI backend. I built on Next.js with Supabase (managed PostgreSQL) on Vercel, which let me ship alone without running a separate API server. Because the business rules sat in database functions, the switch did not change any requirement.

Spending against a budget is calculated, never stored

A stored total goes stale whenever someone backdates, edits or deletes an entry. Calculating it from transactions keeps every month correct (BR-13).

Transfers waited for sign-off

UC-06 was fully specified but held back until the product owner confirmed it belonged in the MVP, instead of being built on assumption.

Budgets moved to Phase 2

The gap analysis showed the core still works without alerts, so the MVP stayed small and shipped sooner.

10 · Reflection

What I learned and what I would do next

  • Define success metrics in the first session. My elicitation checklist left the KPI question open. The 15-second entry target came later; next time I would agree on it up front and measure it after launch.
  • Logging open questions pays off. Writing down what was unclear, and what it would affect, kept the build moving without hiding risks.
  • Thinking in data helps requirements. Asking “what will the data need to answer?” surfaced rules like atomic transfers and soft deletes early, before they turned into bugs.
  • Next step: a full requirement traceability matrix linking each requirement to its user stories, acceptance criteria and test cases.
